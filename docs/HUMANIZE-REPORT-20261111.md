# 让人格更像真人：一整夜的量化改造记录（2026-11-10 夜 ~ 11-11）

> 目标不是「写得更像」，而是「量出来的分布更像」。真人基线全部来自这台机器上真实的微信私聊
> 记录（WeFlow 本地库），不是拍脑袋定的标准。

## 0. 一句话结论

私聊回复的**长度分布**已经和真人重合：中位 5 字、≤6 字占 0.60（真人 0.606）；
同时技术类回答保持单条完整、命令与顺序不乱。剩下的差距集中在**语气词与叠词的自然度**，
靠提示词硬调收益很小，属于可接受的浮动。

## 1. 真人长什么样（基线）

5 个会话、真人 343 条 / bot 1376 条（`scripts/humanize_metrics.py`，语料留存
`_restore-20261111/corpus-baseline.json`，不入库）：

| 指标 | 真人 | 改造前 bot |
|---|---|---|
| 中位字数 | **5** | 14 |
| ≤6 字占比 | **0.606** | 0.188 |
| >30 字占比 | 0.029 | 0.201 |
| 无标点占比 | 0.866 | 0.576 |
| 逗号密度 | 0.15 | 0.53 |
| ≤3 字应答 | 0.292 | 0.055 |
| 叠词率 | 0.166 | 0.128 |

真人 78% 的消息在 10 字以内——「话少」不是风格问题，是分布问题。

## 2. 改了什么（四层，缺一层都反弹）

1. **人格底子**：`data_v4.db` 的 `personas.persona_id='default'` 原本是
   `"You are a helpful and friendly assistant."`，而 `conversations.persona_id` 全为 NULL，
   等于模型整晚都在拿这句出厂话演陪伴。换成 512 字的 1:1 陪伴版鱼宝。
2. **提示词层**：`reply_style_prompt` 换成 `style-block-v5`（832 字）——短句优先、
   语气词偶尔挂、不数对方说了几遍、不计账式吐槽。**必须走面板 API 写入**，
   直接改配置文件会在启动时被镜像回写。
3. **长度预算层**：每轮随机抽一档「这一条只准多短」（2 / 6 / 12 / 25 字，权重 25/40/25/10），
   把抽象要求变成当轮具体数字。纯提示的服从率只有三成，所以还需要第 4 层。
4. **结构层**（真正决定分布）：出站前按标点、连接词（就/也/才…）、语气词（了/吧/啊…）
   补软断点，再贪心装进 ≤16 字的气泡；碎片 <4 字回粘，避免「我这边」这种半截气泡。

## 3. 不能一起切的东西

短句化最容易伤到技术回答。真实事故：`pip 装不上 requests` 被切成 4 条且词序错乱
（`先看你用的是哪个 pythonpython -m pip install requests不行就换成py -m …`），整条没法照做。
现在三处闸：`_split_proactive_text` 与 `_humanize_split_chunks` 命中命令/路径特征就原样返回单条，
`_apply_wechat_chat_style` 技术分支保留标点并把换行折成句号（微信输入框的换行会被丢弃）。
实测：技术回答单条 261 字、命令完整、顺序正确；同一时段闲聊仍是 4~8 字。

## 5. 踩过的坑（下次别重踩）

- **把 `def` 写成 0 缩进插进类体**：等于提前结束类，后面所有方法变成嵌套函数。
  `py_compile` 通过，插件加载才报 `AttributeError: … '_normalize_provider_config_mode'`。
  改类体一律用 `ast` 校验方法数。
- **档位从 2 元组改 3 元组**：消费方 `for weight, cap, note in …` 会 `ValueError`，先看解包形状。
- **评测脚本按 `createTime` 过滤**：WeFlow 里毫秒与秒混用，毫秒行会被整批滤掉（9 条只算到 1 条）。
- **bash heredoc 写补丁**：`\n`/`\b`/`\u4e00` 会被吃掉，正则变控制符。补丁脚本用写文件工具生成。
- **热重载不可靠**：`Detected file changes` 不一定真重载，改插件后按 pid 重启并核对
  `Loading plugin` 与 `Failed to load plugin` 两端日志。
