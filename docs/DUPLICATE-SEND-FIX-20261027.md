# 复读（同一条消息连发 N 遍）修复记录 — 2026-10-27

## 现象

点歌/翻唱完成后，微信里同一句话连发 4~18 条：

| 文本 | 条数 | 时间跨度 |
|---|---|---|
| 已成功使用 SVC 音色【Saya】生成《使一颗心…》 | 18 | 14:19:34 → 14:23:27 |
| 好啦好啦～《落叶归根》翻唱完成啦… | 6 | 09:15:18 → 09:17:43 |
| 卷子分完了没 | 9 | 20:10:37 → 20:14:31 |
| 嘿～你要的《落叶归根》翻唱做好啦… | 5~6 | 18:39:00 前后 |

## 两条独立的重复来源

### ① 插件/AstrBot 侧在几秒内把同一条回复投多次

`09:25:57 / 09:25:58 / 09:25:59 / 09:26:00` 连续 4 个 `send_private_msg`（echo seq 7/10/13/16）——不是 20 秒节奏，是插件把「翻唱完成」这一条回复投了 4 次（拆分组件 + 结果回执 + 持久化回执各发一次）。

### ② 重发队列每 20 秒重放「回读没确认到」的消息，而它其实早就发出去了

- `wxui_queue_interval = 20`（配置项），队列每 20 秒 `drain_queue()` 一轮。
- 发送是否成功，靠读微信数据库回读确认（`verify`）。回读受 BOM、WeFlow 500、worker 僵死、DB 延迟影响，**经常判不出结论**。
- 旧逻辑只在 `ok=True` 时记指纹 → 回读超时（用户C那条要 90 秒才超时）时 `ok=False`，没记指纹 → 下一轮再发一遍，每轮都真的发出去 → 60 秒 3 条、5 分钟 15 条。

20 秒这个节奏就是复读的直接指纹（数据里同文本间隔 ~19-20 秒）。

## 修复（全部在 `akasha-bridge/wxui_sender.py`，发送的唯一收口）

1. **入口去重（文本 / 图片 / 文件三条通道）**
   - `_content_key(kind, spec, target)` 归一化：正文去空白、去首尾标点（`。．.!！?？~～…,，、;；:：` 引号等），图片/文件取文件名。
     → 插件投来的「好啦好啦～…」「好啦好啦…」「好啦好啦！！」视为同一条。
   - 命中「已确认送达」缓存（300 秒）或「刚尝试过」缓存（120 秒）→ 直接返回 `True` 丢弃，日志 `🔁 同内容消息 … 跳过重复投递`。
2. **尝试记录与送达记录分离**
   - `wxui_recent_attempts.json`（120 秒）：只表示「动作可能已执行」，用于抑制重放；
   - `wxui_recent_sends.json`（300 秒）：只表示「已确认送达」，用于入口去重。
   - 发送前写 attempt，发送成功再写 send。**关键**：attempt 不会让消息被误判成已送达而丢掉。
3. **重发队列**
   - 重放前先只读 `verify`（原有逻辑），能确认已送达就直接丢弃；
   - 同内容 300 秒内确认发过 → 按已送达丢弃；
   - 120 秒内刚尝试过（未确认）→ 本轮跳过并留在队列（`⏳ 近期已尝试发送但未确认，本轮不重放`），既不刷屏也不丢；
   - 修正 `send-file` 重放被当成 `send` 的 bug（原来报 `empty text: caller passed None`）。
4. **配套**：队列/去重缓存落盘、重启不丢；`_drop_asset` 仍会清理临时文件。

## 验证

| 场景 | 结果 |
|---|---|
| 同文连发 3 次 | 只送达 1 条（localId 327），后两条 `🔁 跳过` |
| 标点变体「～」「」「！！」 | 只送达 1 条，另两条 `🔁 跳过` |
| 不同内容 | 正常送达（localId 328） |
| 100 秒静默观察 | 无任何重复发送 |

## 回滚

改回旧的纯「成功才记账」即可，关键是 `_remember_attempt` 与 `_attempted_recently` 两处调用；或直接把 `_dedupe_window_s` / `_attempt_hold_s` 调小。

## 已知剩余

- `用户C` 会话单条发送要 90 秒才超时（其他会话 4~5 秒），会让队列变慢；但不会再造成刷屏（attempt 抑制）。
- 插件侧仍然会一次投多条（同一文本），现在被 bridge 收口吸收；要彻底干净需要改 `astrbot_plugin_matsuko_cover` 的发送点（未做）。
