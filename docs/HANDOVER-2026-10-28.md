### 3.1 气声歌翻唱三宗罪（`docs/COVER-GAS-VOICE-FIX-20261024.md`）

用户反馈（孙燕姿《我不难过》自翻唱）：没有强弱、前奏莫名哼唱、咬字差（气声多的歌尤其差）。

根因三条，全部在 `rvc-backend/server.py`：

1. **开头哼唱** = `apply_vocal_gate()` 的兜底增益 `np.maximum(env, GATE_FLOOR*0.5)`（`GATE_FLOOR=0.12`
   → 不唱歌的帧永远有 -24 dB），SVC 把前奏钢琴当旋律唱出来；这首歌第一句在 31.42 s。
2. **没有强弱** = SVC 的 `infer()` 只有内容特征 + 音高 + 音素级 speaker，**没有响度条件**；
   原后处理 `energy_gate` 在峰值 -30 dB 内恒为 1.0，`mix_and_export` 只做峰值归一。
3. **咬字差** = 高频被砍两道：SVC 直出已暗 4~6 dB，`clean_vocal_output()` 齿音压制再砍 2~3 dB，
   `>16k *= 0.5`；且 HNR 比原唱高 4 dB（气声/呼吸噪声被门限抹平）。

改动（全部有环境变量开关，默认开）：

| --- | --- | --- |
| `apply_vocal_gate` | `server.py:849` | `GATE_HARD`：歌词外真静音（行首 0.2 s 淡入、行尾 220 ms 收尾） |
| `match_dynamics` | `server.py:707` | 逐帧 20 ms 把参考的 dB 曲线贴回成品（clip ±18 dB，3 帧平滑） |
| `restore_timbre` | `server.py:758` | 静态 9 段长时谱（±12 dB）+ 2–6k/6–12k 逐帧包络 + 4k–16k 辅音移植 |

### 3.3 合唱源翻唱（`docs/DUET-SPLIT-20261027.md`）

《落叶归根》（王力宏/单依纯合唱）三连反馈：跑调、音色怪、破音。

根因：`vocals.wav` 是两人叠加 → `auto_key_shift()` 用逐帧 f0 中位数判男女调，男声帧把
`low160` 顶到 0.283 > 0.28 误判成男调 → 硬加 +8 半音；`restore_timbre()` 把两个人的混合音色
逐带移植到单一音色；`match_dynamics()` 上行 +18 dB 把噪声底一起放大（实测增益跨度 27~28 dB）。

方案：

1. `_pitch_profile()` 双声源检测 `duet = male > 0.15 and (female + high) > 0.25` → 命中直接 `return 0`；
   同时把男调判定从 `med < 200 or low160 > 0.28` 收紧为 `med < 190 and low160 > 0.45`。
2. `split_duet_vocals()`：逐帧 parselmouth f0 → 男女帧判定 → 5 帧滑窗软化 →
   **谐波梳状掩码**（`exp(-(dist/0.10)^2)`）→ 两轨功率归一等能量 → ISTFT。
   实测男声轨 f0 146.3 Hz / 男声帧 78.4%，女声轨 297.2 Hz / 女声帧 85.6%，分离 7.2 s。
3. `convert_duet_tracks()`：每轨各自变调（男 +8、女 0）→ 各自 SVC →
   各自音色还原（参考就是本轨）→ RMS 对齐合并。
   开关：`BACKEND_DUET_MODE=both|single`、`BACKEND_DUET_SPLIT=0`、`BACKEND_DUET_SAFE=0`。
4. 后处理限幅（见 §3.1 末尾表）。

> ⚠️ **`split_duet_vocals` / `convert_duet_tracks` 现在不在 `server.py` 里**，只在
> `rvc-backend/server.py.broken-2139:615`（10-27 21:39 的损坏版，38,100 B）。原因见 §3.7 的
> 「21:39 误删事故」：恢复用的影子副本是 09:31 的（早于 13:12 的拆轨开发），之后只补回了
> 「双声源检测 → 不变调」和「自动避开合唱版」，**拆轨那条支路（`convert()` 的 duet 分支、
> payload 里的 `duet_split`/`stem`）没有补**。要恢复合唱拆分能力，需要从 `.broken-2139` 里
> 把这两个函数和 `convert()` 的分支合并回来——这是当前最明确的回归项之一（见 §5-2）。

**自动避开合唱版**（用户 13:43 的要求）：`_DUET_WORDS` / `_song_row_info()` / `_score_song_row()` /

### 3.4 日程生成错误 / 缓存命中 / token（`docs/TOKEN-CACHE-FIX-20261025.md`）

四个根因：

1. **日程「错误」= DeepSeek 402 欠费**（余额已充，12:43:50 起成功）；`generate_daily_plan` 对格式
   错误/超时会整份重发 prompt 最多 4 次 → 一次失败 = 4 × ~10K token。
2. **失败调用按字符估算记账，反掐预算**：`token_budget.py` 的 `_estimate_token_count` 高估约 35%，
   401/402 这类「计费前就被拒」也计入 `totals`/`by_day` → 871K 假消耗吃光日限额，日程/主动消息被 defer。
   修复：`_UNBILLED_LLM_ERROR_MARKERS` + `_llm_error_is_unbilled()`，命中时七个计数清零（`calls`/`errors` 仍记）。
3. **prompt 中段时间戳打断缓存前缀**：`当前时间：…` 在 A 段中间，分钟级变化 → 缓存前缀只覆盖
   静态头部 3,840 token（39%）。修复：删掉 A 段时间行，改为**整份 prompt 末尾**追加一行
   「请求时间戳（只用于判断昼夜…）」。
4. **插件 `max_tokens` 被 AstrBot 静默丢弃**：`openai_source._prepare_chat_payload()` 只透传
   `messages`/`model`。直接强制生效会出事（deepseek-flash 是思考模型，8 token 全被 reasoning 吃掉、
   正文为空），所以最终方案是 `[dsh-patch][short-call]`：**只有 `max_tokens<=200` 的判定类调用**
   才生效 `max_tokens` 并对 deepseek 加 `thinking={"type":"disabled"}`；大调用不动。
   实测 `max_tokens=8 → output=1, text='2'`。

验证与结论：

- 用真实渲染的日程 prompt 连打两次 DeepSeek：第 2 次 `cached 3,968 / prompt 4,120` = **96.3%**。
- 10-26 07:32 真实调度仍是 **39%**：`cached 3,840` 恰好是静态头部，`A｜硬约束` 一开头就是
  按天变的 `calendar_context`。所以 39% 是**结构性比例**，不是修复失效。
  10-26 追加两改：A 段重排（静态身份文本前移）、流式路径加 `[dsh-patch][cache-diag-stream]`
  诊断（聊天回复走 `text_chat_stream`，之前完全不可观测、也不进账本）。
- **token 大头在流式聊天**：DeepSeek 面板 10/25 166 次 / **95,288,109 token**，平均 574K/次；
  插件账本同日只有 94.7 万 prompt。7 天非流式后台任务合计 48.5M 字符 ≈ 30M token，

## 6. 坑清单（新旧合并）

**上下文/会话类**

- 单会话上下文：>750K 会触发 preflight 失败（`context ~854864 exceeds 750000`），>1.04M 直接被上游
  400 拒（10-28 00:11 就是这么丢掉「写下交接文档」那一轮的）。长任务要先 `compress` 再继续。
- 存档 session 的 `assistant/message` 正文在 `data.message.content` 的嵌套里，
  `tool/call` 的 `data.arguments` 是 JSON 字符串要二次解析。摘要脚本见 `session-extract/make_digest.py`。
- 控制台是 GBK：Python 直接 `print` 中文/`•` 会 `UnicodeEncodeError`——写 UTF-8 文件再用 read 工具读。

**命令/沙箱类**

- `powershell -File` 一律要 `-ExecutionPolicy Bypass`。
- `Get-NetTCPConnection` 在受限环境会误判端口为空（`Cannot find empty port in range`）→ 用 `netstat -ano`。
- 对 37 GB 的树跑 `du -sh */`、`find -newermt` 会挂几分钟以上；要体积/文件数用
  `xerj autoindex <dir> --walk-only`（1~2 秒）。
- 沙箱里有时看不到进程/窗口（旧记录），必要时让用户以管理员启动 DSH。

**媒体/音频类**

- 成品 mp3 反推人声时必须补 **MP3 编码器延迟 1104 样本（25 ms）**，否则相关系数会假到 -0.02。
- 结果缓存键必须带 **`fx` 指纹**（rvc 后处理开关组合）；歌曲搜索缓存键带 `v2|`。
  **改了后处理不换 key = 拿到旧 mp3**（10-24 最初「改完没反应」就是这个）。
- `--two-stems=vocals` 的分离缓存键 = 歌曲 sha256。

**WeFlow / 微信类**

- WeFlow 只能 5.0.0 补丁版；6.3.2 的 DLL 有「构建日 +15 天」硬时限，不可修。
- 6.3.2 与 5.0.0 不同时跑；启动前清 `ELECTRON_RUN_AS_NODE`。
- 微信会弹独立会话窗口（`Qt51514QWindowIcon`），会挡住定位/打字 → `wechat_cleanup.py --apply`。

**XERJ 类（本轮新增）**

- `xerj` 只是客户端；`xerj mcp` 也不起节点。节点要手动起：
  `xerj --insecure --data-dir %USERPROFILE%\.xerj-code\data`。
- **数据目录必须在项目外**：`xerj` 默认 `--data-dir ./data`，旧会话在项目里跑过一次，
  于是 `wechat-ai-stack/data/autoindex-catalog` 成了污染目录（已加进 `.xerjignore`）。
- autoindex 会 hash 文件；跑到**被进程独占的文件**（`astrbot/astrbot.lock`、`*.db`、sqlite）会
  `os error 33 另一个程序已锁定文件的一部分` 并整轮 abort。已在 `.xerjignore` 排除
  `*.lock`/`*.db*`/`*.sqlite*`。
